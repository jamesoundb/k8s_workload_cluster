# Kubernetes Workload Cluster

This project creates AMD64 worker nodes on Proxmox VMs and joins them to an existing ARM64 Kubernetes control plane cluster using a completely self-contained Ansible automation stack.

## Architecture

- **Control Plane**: 3x Raspberry Pi nodes (ARM64) at 192.168.1.80-82
- **Worker Nodes**: 3x Proxmox VMs (AMD64) at 192.168.1.83-85
- **Virtual IP**: 192.168.1.100 (control plane HA)
- **Container Runtime**: containerd 1.7.28
- **CNI**: Flannel (extending existing control plane network)

## Components

### Terraform Infrastructure
- Creates Ubuntu 24.04 cloud-init template (VM ID 9001)
- Provisions 3x worker VMs with static IPs and MAC addresses
- Configures cloud-init with SSH keys and network settings
- Generates Ansible inventory automatically

### Self-Contained Ansible Automation
**Roles:**
- `common`: OS preparation optimized for AMD64 workers
- `containerd`: Container runtime installation and configuration
- `kubernetes`: Kubernetes package installation (kubelet, kubeadm, kubectl)
- `worker`: Cluster joining, labeling, and verification

**Playbooks:**
- `join-workers.yml`: Complete end-to-end worker deployment
- `reset-workers.yml`: Clean worker reset for testing and troubleshooting

**Features:**
- No external dependencies on other projects
- Architecture-aware (AMD64 vs ARM64 optimizations)
- Complete end-to-end worker provisioning
- Comprehensive verification and testing

### Scripts
- `scripts/create_worker_template.sh`: Creates optimized VM template
- `scripts/test_worker_template.sh`: Tests template deployment
- `scripts/cleanup_workers.sh`: Removes VMs and templates
- `validate.sh`: Pre-deployment validation

## Quick Start

1. **Prerequisites**
   ```bash
   # Ensure SSH key exists
   ls ~/.ssh/proxmox*
   
   # Validate environment
   ./validate.sh
   ```

2. **Create Template**
   ```bash
   ./scripts/create_worker_template.sh
   ```

3. **Deploy Infrastructure**
   ```bash
   cd terraform
   terraform init
   terraform plan
   terraform apply
   ```

4. **Configure Workers**
   ```bash
   cd ../ansible
   ansible-playbook -i generated_inventory.yml join-workers.yml
   ```

5. **Reset Workers (if needed)**
   ```bash
   ansible-playbook -i generated_inventory.yml reset-workers.yml
   ```

6. **Verify Deployment**
   ```bash
   # From control plane
   kubectl get nodes -o wide
   kubectl get pods -A
   ```

- **Worker IPs**: 192.168.1.83-85

## Reset and Testing

### Worker Reset
For testing or troubleshooting, you can reset workers to clean state:
```bash
cd ansible
ansible-playbook -i generated_inventory.yml reset-workers.yml
```

The reset playbook:
- Gracefully drains and removes nodes from cluster
- Cleans up Kubernetes packages and configuration
- Removes container runtime and networking
- Verifies clean state

## Advanced Usage

### Custom Worker Configuration
Modify role variables in `join-workers.yml`:
```yaml
- role: worker
  vars:
    worker_max_pods: 300
    worker_labels:
      - "node-role.kubernetes.io/worker="
      - "workload-type=compute-intensive"
```

### Architecture-Specific Settings
The roles automatically detect architecture:
```yaml
# In containerd role defaults
arch_map:
  "x86_64": "amd64"
  "aarch64": "arm64"
download_arch: "{{ arch_map[ansible_architecture] }}"
```

### DNS Configuration
Workers use Pi-hole (192.168.1.3) by default. DNS is configured in the common role to ensure proper external resolution.

## Troubleshooting

### Common Issues

**Role Not Found**
```bash
# Verify roles directory structure
ls -la ansible/roles/
ansible-playbook --list-tasks join-workers.yml
```

**SSH Connection Failed**
```bash
# Test SSH connectivity
ssh -i ~/.ssh/proxmox k8s_83@192.168.1.83

# Check generated inventory
cat ansible/generated_inventory.yml
```

**Worker Join Failures**
```bash
# Run with increased verbosity
ansible-playbook -i generated_inventory.yml join-workers.yml -vv

# Check specific role execution
ansible-playbook -i generated_inventory.yml join-workers.yml --tags worker
```

## Verification

The automation includes comprehensive verification:

1. **Node Health Checks**: CPU, memory, disk space
2. **Service Verification**: containerd, kubelet status
3. **Cluster Integration**: Node Ready status, label application
4. **Workload Testing**: Pod scheduling verification
5. **Network Validation**: Container networking functionality

### Manual Verification
```bash
# Check all nodes
kubectl get nodes -o wide

# Verify worker labels
kubectl get nodes --show-labels | grep worker

# Test workload scheduling
kubectl run test-pod --image=nginx --restart=Never \
  --overrides='{"spec":{"nodeSelector":{"node-role.kubernetes.io/worker":""}}}'
```

## Integration

This self-contained worker cluster:
- **Connects to existing control plane**: Via VIP at 192.168.1.100
- **Extends CNI network**: Integrates with existing Flannel configuration
- **Maintains cluster consistency**: Same Kubernetes version and runtime
- **Operates independently**: No shared files or external role dependencies
